# 財務分析引擎

`src/lib/financeAnalytics.ts`

## 為什麼要有這個東西

同樣三個問題 —— 這個月花多少、哪一類變多了、有沒有接近預算 —— 原本在三個地方
各算一次：Dashboard 裡一段 90 行的 `useMemo`、桌寵的顯示狀態、以及 AI 自己從
原始交易列去算。

一個計算有三份實作，就有三次互相矛盾的機會，而**最容易安靜出錯的是 AI**，
因為沒有人會去驗算它的加總。

```
FinanceRepository ──> FinanceAnalyticsEngine ──┬──> UI
                                               ├──> 🐣 Pet
                                               └──> AI
```

## 兩條硬規則

1. 所有 today / this week / this month 都是**使用者裝置本地**的日曆邊界，
   一律透過 `./datetime`。程式碼裡不存在 `toISOString().split('T')[0]`。
2. 所有加總走 `./money` 的整數 minor unit。在財務 App 裡顯示
   `NT$ 0.30000000000000004` 不是四捨五入的趣聞，是錯的數字。

## 已完成的指標

| 指標 | 方法 |
|---|---|
| 今日 / 本週 / 本月 收支與筆數 | `totalsFor()` |
| 與上一期比較（金額 + 百分比） | `getSummary()` |
| 分類占比與各分類變化 | `getCategoryBreakdown()` |
| 預算使用率與狀態 | `getBudgetStatus()` |
| 固定支出比例 | `getFixedCostRatio()` |
| 儲蓄率 | `getSavingsRate()` |
| 負債總覽 / 已還金額 / 最高利率 | `getDebtSummary()` |
| 目標進度與每月所需 | `getGoalStatus()` |
| 期間內交易查詢 | `getTransactionsByRange()` |
| 完整結果 | `analyze()` |

## 容易錯、而且已被測試釘住的地方

**週從星期一開始。** `getDay()` 星期日回傳 0，所以星期日要對應到 6 而不是 0。
弄錯的話每一筆週統計都會安靜地偏移一天，而且星期日會自成一週。

**月比較用的是上一個「日曆月」**，不是「30 天前」。拿三月跟「二月加幾天」比是
安靜的錯誤。

**基期為零時回傳 `null`，不是 Infinity 或 100%。** 「從 0 變成有」報成
「成長 100%」是一個看起來很戲劇化、但沒有任何意義的數字。

## 不羞辱

`buildInsights()` 只陳述事實然後停住。有一條測試直接斷言：即使帳本超出預算
33 倍，輸出也不會包含「亂花」「浪費」「太多」「不該」。

## 效能

建構時做一次 day/month 索引，之後的查詢讀索引。實測（數字會印進 CI log）：

| 情境 | 時間 |
|---|---|
| 50,000 筆建索引 | 6–11 ms |
| 50,000 筆 `analyze('month')` | ~3 ms |
| 50,000 筆跑 12 次分類分解 | ~6 ms |

複雜度守門測試是**刻意設計成能真的抓到退化**的：拿 5k 帳本比 50k 帳本毫無意義，
因為大帳本在被查詢的那個月裡本來就有 ~10 倍的列，誠實的工作量就足以解釋差距，
full scan 可以藏在裡面。所以測試把「被查詢月份」固定在 2,000 筆，只改變月份
**之外**的歷史資料量：16 倍的額外歷史，耗時 2.2ms → 2.3ms。

這個守門本身也驗證過：把日索引換成 full scan，數字跳到 27.8ms，測試確實失敗。
